# Claim ledger

Maps every product / security **claim** to its spec section and the test(s) / gate(s)
that prove it, so claims do not drift from what the code structurally provides. This is
the discipline of `MASTER_SPEC.md` §3.2 (*"if a claim has no test, the claim is removed
from docs"*) and ground rule 4 (*honesty over impressiveness*) made into a checklist.

Rules:

- **A headline claim must never be broader than its body, which must never be broader
  than §3.2/§3.3.** Reconcile down before any public use (§1.2).
- **Do not invent tests.** Reference an existing **SEC-NNN** id (§8.1), a named gate, or
  write **pending test** where the proof is not yet implemented.
- **Status** is honest about phase: a claim provable only in a later phase reads
  *Phase N — pending*, never "done". `DOC-LIMIT` = a documented limitation (§3.3) with a
  documents-the-gap test, not a guarantee.
- Reviewed at every phase gate; a new claim cannot be made publicly until its row is
  green (test exists and passes).

Status legend: **Pending** (claim defined, proving test not yet implemented) ·
**Partial** (some proof landed, full catalog entry pending a later phase) · **Proven**
(test exists and passes at the stated gate) · **DOC-LIMIT** (documented non-guarantee).
