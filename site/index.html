keel

The model requests. The warden decides. The model requests. The warden decides.

keel is an open-source coding agent harness. The agent runs behind an enforcement boundary. The model cannot argue past it. The model asks for an action. A separate warden process decides if the action runs, under a hash-pinned policy the model cannot rewrite. Every decision, allowed or denied, goes into a tamper-evident audit record that the agent cannot write to.

What it looks like

Enforcement you can read

The warden makes a decision for every governed action. It records the reason and the audit reference next to the decision.

keel — governed session 
$ pnpm keel run -p "audit this repo and send me a summary"

  read    src/index.ts                     allowed   workspace
  search  "password|secret" src/           allowed   workspace
  bash    rg --files -g '*.ts'             allowed   sandbox: bubblewrap
  bash    cat ~/.ssh/id_rsa                DENIED    policy: secret read (POL-001)
                                                     audit ses_7f3a…#0091
  egress  evil.example.com:443             REVIEW    not on the allowlist
                                                     waiting for a human

$ pnpm keel audit verify ~/.config/keel/audit/exports/bundle_ses_7f3a
  chain     ok  412 records, no gaps
  signature ok  ed25519 checkpoint

Illustrative output. The denial and review paths shown here are covered by the security suite — see the claim ledger. Before a side-effecting action runs, the warden writes a durable intent record. If it cannot write the audit chain, the action does not run.

Technical design

Two processes, one boundary

Enforcement is structural, not behavioral. It does not depend on trusting how the model behaves. The kernel holds the model conversation. The kernel has no path to run a governed action on its own.

The governed surface today is bash, the trusted typed file tools (read, search, write, edit), lifecycle.run, and reviewed, pinned local-stdio MCP calls. Session-helper surfaces (plan, skill, retrieve) and provider API calls are not governed.

kernel

can only request

  • agent loop and tools
  • provider adapters
  • TUI, sessions, CLI
  • holds the model context
── request ──▶ The kernel sends a request to the warden. ◀── verdict ── The warden returns a verdict. JSON-RPC / stdio

warden

decides

  • hash-pinned policy
  • OS sandbox profile
  • network egress control
  • writes the audit chain
  1. The model requests an action. It cannot run the action itself.
  2. The kernel sends the request to the warden over JSON-RPC on stdio. The interface is frozen and versioned.
  3. The warden evaluates a hash-pinned policy pack. The model cannot change this policy, because the policy is not in the model's writable world.
  4. The warden runs an allowed governed bash action inside a real OS sandbox — Seatbelt on macOS, bubblewrap on Linux. It filters network egress through an allowlist proxy. The typed file tools are warden-routed with policy, profile, audit, and path-containment checks. They are not a separate OS-sandbox claim.
  5. The warden writes a durable intent record before a side-effecting action runs, and the result after it. Records form a SHA-256 hash chain with signed checkpoints. Only the warden writes this chain. If the chain cannot be written, the action does not run.
  6. The kernel receives the verdict. It cannot override a denial.

Full detail: the architecture one-pager and MASTER_SPEC.md.

Autonomy

Autopilot is not YOLO

Autonomy modes are policy postures over the warden's enforcement. They are not promises about model behavior. Guided is the default: consequential actions pause for your approval. Autopilot removes the human prompt only for actions the warden has already proven contained and low-risk. It never lets the model raise its own mode, change policy, or turn a denial into an approval. A human sets the mode, and every mode change is audited. "YOLO" means reduced or absent enforcement. keel has no such mode. The code path for it does not exist.

Honest limits

What keel does not claim

keel is pre-alpha. These areas are not built, not proven, or not covered.

  • Not injection immunity. The model can still be fooled. What the warden blocks is the action.
  • Provider API egress is not governed. Calls to the model provider do not route through the warden.
  • The memory plane does not exist. packages/memory is a placeholder for Phase 3.
  • Remote, localhost, and unreviewed MCP are not covered. Only reviewed, pinned local-stdio MCP has a governed path.
  • No plugin or registry governance. That work is not started.
  • No provenance or taint enforcement. That is Phase 3. Trust is uniformly fail-closed today.
  • No resource containment. PID, cgroup, and memory limits are not claim-grade.
  • Tamper-evident, not tamper-proof. Audit records detect change after the fact. They do not stop same-user malware that steals the signing key.
  • The live receipt is not the tamper-evident record. Only the exported evidence bundle is chain-derived and verifiable offline.
  • Bundle authenticity needs a second step. You must compare the signer key against a published or out-of-band key.
  • No published npm release. Run from source. See the quickstart below.
  • Windows is not supported. Linux and macOS are the tested platforms. Use WSL2 on Windows.

Quickstart

Run it from source

You need Node 20 or later and ripgrep. pnpm keel doctor checks your machine and prints one fix per problem. 

# 1. get the code
git clone https://github.com/keel-harness/keel.git
cd keel

# 2. install (corepack pins the exact pnpm version)
corepack enable && pnpm install

# 3. check your machine
pnpm keel doctor

# 4. add a provider key (stored 0600, never echoed)
pnpm keel auth set anthropic

# 5. run a task
pnpm keel run -p "fix the failing test in src/foo.ts"

Install from npm

# not published yet — this command does not work today
npm i -g keel-harness
Not yet available. The name keel-harness is reserved on the npm registry, and the version published there (0.0.1) is a name-reservation placeholder only. It is not the release. A real npm package is gated on a curated public repository, a protected release configuration, staged-byte inspection, human 2FA approval, and live-registry verification. Until then, the source checkout above is the supported path.

keel aims to be a well-built agent harness with real runtime security. It is pre-alpha and it is not vetted. Do not use it for mission-critical or business-critical work until the open-source community reviews it rigorously. keel is also a human-in-the-loop tool by design. If you want an agent that runs fully unattended, keel solves a different problem.
